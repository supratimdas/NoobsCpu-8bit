A step-by-step walkthrough using the NoobsC compiler targeting a real 8-bit CPU

A compiler is just a program that reads text in one language and produces equivalent text (or binary) in another. This guide walks every stage of the NoobsC compiler — from reading raw characters all the way down to machine-code bytes — with concrete examples from a real, working codebase.

Running Example

Background

The Target Architecture: NoobsCpu-8bit

Before writing a compiler you must deeply understand the machine you're targeting. Every code generation decision flows from the hardware.

Hardware Specs

  • 4 registers: R0, R1, R2, R3 (8-bit each)
  • Harvard architecture: separate instruction and data memory
  • 2 KB instruction memory, 2 KB data memory
  • 8-bit data bus — all values 0–255
  • 3-stage pipeline: Fetch → Decode → Execute

Status Register (SR)

SR[2]NZresult != 0
SR[0]OVFsubtraction borrowed (underflow)

SUB follows the conventional Rd = Rd − Rs rule

SUB R0,R1 computes R0 = R0 − R1, storing the result back in the first operand — the same convention as most ISAs. The OVF flag is set whenever the result underflows (borrows), making it useful for comparisons. See the Debugging section for the historical ISA bug that required an earlier codegen workaround.

Phase 1

Lexical Analysis — The Lexer

Theory

Source code is just a long string of characters. The lexer (also called a scanner or tokenizer) groups those characters into meaningful units called tokens. Think of it like identifying words and punctuation in a sentence before you try to understand the grammar.

Concrete Example

The input n = n - 1; becomes:

Token(IDENT,   "n"  , 1:1)
Token(EQ,            1:3)
Token(IDENT,   "n"  , 1:5)
Token(MINUS,         1:7)
Token(INT_LIT, 1    , 1:9)
Token(SEMI,          1:10)Token stream

The parser sees this clean flat list — it never has to worry about whitespace, comments, or character offsets.

Token Types

Every token has a type (what kind of thing is it?), an optional value (what exactly is it?), and a source location (line and column, for error messages).

CategoryExamplesToken type
Integer literals42, 0xFF, 0b1010INT_LIT
Character literals'A', '\n'CHAR_LIT
Identifiersresult, fib, my_varIDENT
Keywordschar, void, while, returnKW_CHAR, etc.
Operators+, -, ==, &&, ++PLUS, etc.
Punctuation(, ), {, ;, ,LPAREN, etc.

Maximal Munch Rule

Theory — Maximal Munch

When two rules could match at the same position, always take the longest match. This rule resolves ambiguities that would otherwise require the lexer to guess.

// "++": one PLUS_PLUS token, not two PLUS tokens
i++
→ IDENT("i"), PLUS_PLUS

// "<=": one LT_EQ token, not LT then EQ
j <= 7
→ IDENT("j"), LT_EQ, INT_LIT(7)

// "charter": full identifier, not KW_CHAR + IDENT("ter")
charter
→ IDENT("charter")Maximal munch examples

The trick is peeking ahead one character before deciding which token to emit:

if ch == '+':
    if self._match('+'): return Token(PLUS_PLUS)   # consumed ++
    if self._match('='): return Token(PLUS_EQ)    # consumed +=
    return Token(PLUS)                              # just +lexer.py — maximal munch for '+'

What the Lexer Throws Away

The lexer discards whitespace and comments — they're meaningful to humans but irrelevant to grammar. NoobsC supports both line comments (// …) and block comments (/* … */). Note: the lexer does NOT support # comments — a common mistake when writing example programs manually.

Why Keywords Are Identifiers First

Keywords like while and char match the same pattern as identifiers ([a-zA-Z_][a-zA-Z0-9_]*). The lexer scans the full word first, then looks it up in a keyword table to decide the token type. This naturally implements maximal munch for keywords.

def _scan_ident_or_keyword(self) -> Token:
    text = ''
    while self._peek() and (self._peek().isalnum() or self._peek() == '_'):
        text += self._advance()
    tt = KEYWORDS.get(text, TokenType.IDENT)  # keyword? or plain ident?
    return Token(tt, text if tt is TokenType.IDENT else None, line, col)lexer.py
Phase 2

Parsing — Building the AST

Theory

The parser reads the flat token stream and builds a tree that captures the hierarchical structure of the program. This tree is called the Abstract Syntax Tree (AST). It is "abstract" because it omits details like parentheses and semicolons — those were only needed to define structure unambiguously, and the tree already encodes that structure.

The Grammar

A grammar is a precise description of what sequences of tokens form valid programs. We use EBNF (Extended Backus-Naur Form) notation:

── Top-level ──────────────────────────────────────────────
program     → declaration*

declaration → var_decl | func_decl

── Declarations ───────────────────────────────────────────
var_decl    → 'char' IDENT ('[' INT_LIT ']')? ('=' expr)? ';'
func_decl   → ('char' | 'void') IDENT '(' param_list? ')' block

── Statements ─────────────────────────────────────────────
statement   → var_decl | if_stmt | while_stmt | for_stmt
            | return_stmt | break_stmt | expr_stmt

── Expressions (lowest to highest precedence) ──────────────
expr        → assign
assign      → logical_or (assign_op assign)?        ← right-assoc
logical_or  → logical_and ('||' logical_and)*
logical_and → bitwise_or  ('&&' bitwise_or)*
bitwise_or  → bitwise_xor ('|'  bitwise_xor)*
bitwise_xor → bitwise_and ('^'  bitwise_and)*
bitwise_and → equality    ('&'  equality)*
equality    → relational  (('=='|'!=') relational)*
relational  → additive    (('<'|'>'|'<='|'>=') additive)*
additive    → multiply    (('+'|'-') multiply)*
multiply    → unary       (('*'|'/'|'%') unary)*
unary       → ('!'|'~'|'-') unary | postfix
postfix     → primary ('++'|'--')?
primary     → INT_LIT | CHAR_LIT | IDENT | IDENT'['expr']'
            | IDENT'('args')' | '('expr')'NoobsC Grammar (EBNF)
Why Does Operator Precedence Come From Grammar Structure?

Notice that + is deeper in the grammar than ||. This means a || b + c will be parsed as a || (b + c), not (a || b) + c — exactly what we expect from standard math precedence. The grammar encodes precedence through nesting depth. The lower in the grammar tree a rule appears, the more tightly it binds.

Recursive Descent Parsing

Theory — Recursive Descent

Recursive descent is the simplest and most readable parsing technique. Each grammar rule becomes one method. The method tries to match that rule's pattern by calling the methods for sub-rules recursively. Because the grammar is naturally recursive (expressions contain sub-expressions), the code structure mirrors the grammar directly.

Here's how n = n - 1 gets parsed. The parser starts at parse_expr(), which calls down through the precedence levels:

parse_expr()
  → parse_assign()
      sees IDENT("n") EQ ...
      left = parse_logical_or()
               ... (descends through levels)
               → parse_primary() → Var("n")
      op = "="
      right = parse_assign()
                → parse_additive()
                    left = Var("n")
                    op   = "-"
                    right = IntLit(1)
                    → BinOp(Var("n"), "-", IntLit(1))
      → Assign(Var("n"), "=", BinOp(Var("n"), "-", IntLit(1)))Parse trace for n = n - 1

The resulting AST node for the whole Fibonacci function looks like this conceptually:

FuncDecl("fib", params=[Param("n")],
  body=Block([
    VarDecl("a"), VarDecl("b"), VarDecl("tmp"),
    Assign(Var("a"), "=", IntLit(0)),
    Assign(Var("b"), "=", IntLit(1)),
    WhileStmt(cond=Var("n"), body=Block([
      Assign(Var("tmp"), "=", Var("b")),
      Assign(Var("b"),   "=", BinOp(Var("a"), "+", Var("b"))),
      Assign(Var("a"),   "=", Var("tmp")),
      Assign(Var("n"),   "=", BinOp(Var("n"), "-", IntLit(1))),
    ])),
    ReturnStmt(Var("a")),
  ])

Phase 3

Semantic Analysis

Theory

The parser verified syntax — does the program match the grammar? The semantic analyser verifies meaning — does it make sense? A program can be syntactically valid but semantically wrong.

x = 5;              ← syntax OK, but what is x?
foo(1, 2);         ← syntax OK, but foo takes 3 args
break;              ← syntax OK, but we're not in a loop
void f() { return 1; }  ← syntax OK, but f is voidSyntactically valid but semantically wrong

Symbol Tables

The central data structure is the symbol table: a dictionary mapping every declared name to a description of what it is.

After analysing our fibonacci program, the symbol table contains:

"result"  →  Symbol(kind='scalar')
"fib"     →  Symbol(kind='func', return_type='char', param_count=1)
"main"    →  Symbol(kind='func', return_type='void', param_count=0)

Inside fib(), a local scope adds:
"n"       →  Symbol(kind='scalar')  ← parameter
"a"       →  Symbol(kind='scalar')
"b"       →  Symbol(kind='scalar')
"tmp"     →  Symbol(kind='scalar')Symbol table after analysis

Scopes

NoobsC has exactly two scope levels:

  • Global scope — top-level variables and functions
  • Local scope — parameters + local variables inside a function body

When we enter a function we push a fresh local scope. When we leave, we pop it. Lookup always checks local first, then global — so a local variable can shadow a global with the same name.

Two-Pass Analysis

Why Two Passes?

Consider two mutually-recursive functions where even() calls odd() and vice versa. In a single pass, when we analyse even() we haven't seen odd() yet, so the call looks like an undeclared function. The solution: hoist all function and global names first (pass 1), then check each function body (pass 2). Now every name is known before any body is analysed.

What Gets Checked

  • Undeclared variable or function
  • Duplicate declaration in the same scope
  • Array used without index: arr instead of arr[i]
  • Scalar used with index: x[i] where x is a plain variable
  • Wrong number of arguments to a function call
  • Void function returning a value; non-void function with no return
  • break used outside a loop
Phase 4

Code Generation

Theory

Code generation is the heart of the compiler. It walks the AST node by node and emits assembly instructions. The key design decisions are: how to map language constructs onto the machine's registers and memory.

Register Roles

With only 4 registers, every register has a fixed role:

RegisterRoleWhen used
R0 Accumulator Every expression result lands here. All _gen_expr() calls guarantee R0 = result on exit.
R1 Secondary Right-hand operand for binary instructions (ADD, SUB, AND, …)
R2 Arg/Temp Third function argument; scratch in nested calls
R3 Array Index Used as the offset in SET_ADR_MODE indexed addressing

Variable Storage

There is no stack-allocated local storage. Instead, every variable gets a static data label in the .data section:

Variable kindAssembly labelExample
Global variablevarnameresult:0x00
Global arrayarrname (N bytes)data:0x00,0x00,…
Local / parameter__funcname_varname__fib_n:0x00
Scratch temp__tmp0 … __tmp3shared across all functions
⚠ No Recursion

Because locals are statically allocated (not on a stack), a recursive function would overwrite its own locals on the second call. NoobsC explicitly disallows recursion.

Generating Expressions

The golden rule: after any _gen_expr(node) call, R0 holds the result. This invariant simplifies the rest of the codegen enormously.

Literals

// IntLit(10) → R0 = 10
    XOR  R0,R0         ; R0 = 0  (clear first)
    ADDI R0,R0,10     ; R0 = 0 + 10 = 10Generated code

Variables

// Var("a") — a local of fib()
    LOAD R0,__fib_a   ; R0 = memory[__fib_a]Generated code

Binary Operations — The Tricky Part

A binary operation like a + b needs both operands in registers at the same time. But we only have R0 as the result register. The solution: evaluate left, save to a temp slot in memory, evaluate right into R0, then restore left from the temp.

// BinOp(Var("a"), "+", Var("b"))
    LOAD  R0,__fib_a    ; R0 = a  (evaluate left)
    STORE R0,__tmp0     ; save left to temp slot
    LOAD  R0,__fib_b    ; R0 = b  (evaluate right)
    ADDI  R1,R0,0      ; R1 = b  (move right to R1)
    LOAD  R0,__tmp0     ; R0 = a  (restore left)
    ADD   R0,R1         ; R0 = a + b ✓Generated code for a + b

Subtraction

Subtraction follows the same left/right pattern as addition. SUB R0,R1 computes R0 − R1, so we put left in R0 and right in R1:

// BinOp(Var("n"), "-", IntLit(1))  →  n - 1

    LOAD  R0,__fib_n    ; R0 = n  (evaluate left)
    STORE R0,__tmp0     ; save left to temp slot
    XOR   R0,R0
    ADDI  R0,R0,1       ; R0 = 1  (evaluate right)
    ADDI  R1,R0,0       ; R1 = 1  (move right to R1)
    LOAD  R0,__tmp0     ; R0 = n  (restore left)
    SUB   R0,R1         ; R0 = R0-R1 = n-1 ✓Generated code for n - 1

Control Flow

The While Loop

A while loop needs two labels: one at the top (to jump back to) and one at the end (to exit to). The condition is evaluated at the top on every iteration.

// while (n) { body }

__while_0: NOP          ; top label

    // evaluate condition: n
    LOAD  R0,__fib_n    ; R0 = n
    ADDI  R0,R0,0       ; dummy add to update Z/NZ flags
    JMPZ  __while_end_1 ; if n==0: exit loop

    ; ... body ...

    JMPNC __while_0     ; unconditional: back to top
__while_end_1: NOP      ; end labelGenerated code for while (n) {…}

Comparison Conditions

For comparisons like j < 7, we use the SUB instruction and the OVF flag to determine the result. The key insight: SUB R0,R1 with R0=left, R1=right sets OVF=1 when left < right (because left−right underflows).

// while (j < 7)

__while_3: NOP

    ; Load j (left) and 7 (right) for comparison
    LOAD  R0,__sort_j      ; R0 = j  (left)
    STORE R0,__tmp0
    XOR   R0,R0
    ADDI  R0,R0,7         ; R0 = 7  (right)
    ADDI  R1,R0,0         ; R1 = 7
    LOAD  R0,__tmp0        ; R0 = j

    SUB   R0,R1            ; R0 = R0-R1 = j-7. OVF=1 if j<7.

    JMPOVF __cmp_skip_5   ; OVF=1 → j<7 is TRUE → skip exit
    JMPNC  __while_end_4  ; OVF=0 → j≥7 is FALSE → exit loop
__cmp_skip_5: NOP

    ; ... body ...

    JMPNC __while_3
__while_end_4: NOPGenerated code for while (j < 7)

Function Calls and the Calling Convention

With only 4 registers and static allocation, the calling convention is simple:

  1. 1
    Evaluate arguments and place them in R0, R1, R2 (up to 3 args)
  2. 2
    Emit CALLNC __funcname — this pushes the return address and jumps
  3. 3
    Callee immediately saves its args from R0/R1/R2 to its static data labels
  4. 4
    Callee does its work, leaving the return value in R0
  5. 5
    Callee emits RET — pops return address and jumps back
  6. 6
    Caller reads the return value from R0
// result = fib(10);   ← the call site in main()
    XOR  R0,R0
    ADDI R0,R0,10       ; R0 = 10  (arg 0)
    CALLNC __fib         ; call fib
    STORE R0,result      ; result = R0  (return value)

// fib() entry — saves its parameter immediately
__fib: STORE R0,__fib_n  ; save arg0 (n) to static slot
    ; ... body ...
    LOAD  R0,__fib_a     ; return value = a
    RETGenerated call + callee entry

Array Access

The CPU supports indexed addressing via SET_ADR_MODE. When this mode is active, every LOAD/STORE accesses Memory[label + R3] instead of Memory[label].

So data[j] generates:

// Reading data[j]
    LOAD  R0,__sort_j    ; R0 = j  (the index)
    ADDI  R3,R0,0       ; R3 = j  (move index to R3)
    SET_ADR_MODE          ; enable indexed addressing
    LOAD  R0,data        ; R0 = Memory[data + R3] = data[j]
    RST_ADR_MODE          ; disable indexed addressing

// Writing data[j] = tmp
    LOAD  R0,__sort_tmp  ; R0 = tmp (value to write)
    STORE R0,__tmp0      ; save value
    LOAD  R0,__sort_j    ; R0 = j  (index)
    ADDI  R3,R0,0       ; R3 = j
    LOAD  R0,__tmp0      ; R0 = tmp (restore value)
    SET_ADR_MODE
    STORE R0,data        ; Memory[data + j] = tmp
    RST_ADR_MODEGenerated code for array read/write
Phase 5

Assembly — From Mnemonics to Bytes

Theory

The assembler converts human-readable instruction mnemonics into binary machine code. Unlike the compiler (which involves significant transformation), the assembler is mostly a mechanical encoding: look up each opcode in a table, encode the register arguments into a byte, handle labels.

Two-Pass Design

The assembler makes two complete passes through the source file:

  • 1
    Pass 1 — Build the symbol table. Scan every label (lines with :) and record what address they correspond to. Count instruction bytes without emitting them. This resolves all forward references — a label used before it's defined.
  • 2
    Pass 2 — Emit machine code. Re-scan from the beginning. Now every label address is known, so jump targets can be encoded as real addresses. 
Example: JMPZ __while_end_1

Pass 1:
  See "__while_end_1: NOP" at code address 0x0042
  → SYMBOL_TABLE["__while_end_1"] = 0x0042

Pass 2:
  See "JMPZ __while_end_1"
  → look up: 0x0042
  → emit: SET_BCZ (1 byte), JMP (1 byte), 0x00 (addr MSB), 0x42 (addr LSB)Two-pass label resolution

Instruction Encoding

Each instruction is encoded as one or two bytes. The byte layout for ALU operations:

Byte layout:  [7:5] opcode  [4] immediate?  [3:2] PTR1 (1st arg reg)  [1:0] PTR0 (2nd arg reg)

Example: ADD R0,R1
  opcode  = ADD  = 0b001 → bits[7:5] = 001
  imm     = 0    (register mode)
  PTR1    = R0   = 0     → bits[3:2] = 00
  PTR0    = R1   = 1     → bits[1:0] = 01

  → 0b001_0_00_01 = 0x21

Example: ADDI R0,R0,10
  opcode  = ADDI = 0b001 → bits[7:5] = 001
  imm     = 1    (immediate mode) → bit[4] = 1
  PTR1    = R0   = 0     → bits[3:2] = 00
  PTR0    = R0   = 0     → bits[1:0] = 00

  → 0b001_1_00_00 = 0x30
  second byte: 0x0A (the immediate value 10)Instruction encoding
Why PTR1 is the "first" text argument

In the assembler source (noobsASM.pl), the first text argument becomes PTR1 (bits[3:2]) and the second text argument becomes PTR0 (bits[1:0]). The execute stage computes src0 − src1. Originally the decode stage assigned src0 = reg[PTR0] = 2nd_arg and src1 = reg[PTR1] = 1st_arg, making SUB R0,R1 = R1−R0 — the reverse of every other ISA. This was corrected by swapping the register assignments in the decode stage for non-immediate SUB only (src0 ← PTR1 = Rd, src1 ← PTR0 = Rs), so that SUB Rd,Rs = Rd − Rs as expected without affecting SUBI. The original bug and both fixes are described in the Debugging section below.

Section Detection — A Fragility

The assembler identifies the .data and .code sections by matching these exact strings against each line. This means any variable or label whose name contains "data" or "code" as a substring would trick the assembler into switching sections mid-program — a subtle but catastrophic bug. The fix: match the exact section markers using anchored regular expressions:

# Fragile (old) — matches any line containing "data"
if($line =~ /data/) { ... }

# Fixed — only matches the exact section header ".data"
if($line =~ /^\.data$/) { ... }noobsASM.pl — section detection fix
Debugging

Real Compiler Bugs — Case Studies

The best way to understand a compiler deeply is to debug a real bug in it. Here are two bugs found and fixed in NoobsC, with a complete analysis of how each was discovered and why it was hard to spot.

Bug 1: The SUB Instruction Bug (Infinite Loop)

Symptom

The compiler-generated Fibonacci program hangs forever instead of computing fib(10)=55.

Step 1 — Isolate the loop

The while loop condition is while (n) — a simple truthiness check. If it ran forever, either n never reaches zero, or the loop condition is broken. The loop condition code uses JMPZ (jump when n==0), which is straightforward. So focus on the decrement: n = n - 1.

Step 2 — Read the generated assembly

; n = n - 1  (ORIGINAL, BUGGY codegen)
    LOAD  R0,__fib_n    ; R0 = n  (left = n)
    STORE R0,__tmp0     ; save left
    XOR   R0,R0
    ADDI  R0,R0,1       ; R0 = 1  (right = 1)
    ADDI  R1,R0,0       ; R1 = 1  (right → R1)
    LOAD  R0,__tmp0      ; R0 = n  (left → R0)
    SUB   R0,R1          ; BUG: ISA was Rs−Rd, so R0 = R1-R0 = 1-n ← WRONG!
    STORE R0,__fib_n    ; stores 1-n instead of n-1Buggy generated assembly

Step 3 — Trace the ISA semantics

Reading the assembler source (noobsASM.pl) reveals how the instruction is encoded:

# For any 2-arg ALU instruction:
my $src_reg1 = to_int($REGISTER_HASH{$ARGLIST[0]}) << 2; # 1st text arg → PTR1 (bits[3:2])
my $src_reg0 = to_int($REGISTER_HASH{$ARGLIST[1]});        # 2nd text arg → PTR0 (bits[1:0])

# Execute: result = src0 - src1  (unchanged)
# Original decode: src0 = reg[PTR0] = reg[2nd_arg] = Rs
#                  src1 = reg[PTR1] = reg[1st_arg] = Rd
# So result = Rs - Rd → SUB R0,R1 → R0 = R1 - R0  ← reversed!noobsASM.pl — encoding reveals reversed semantics

Step 4 — Understand the failure mode

n = 10 on entry to fib(10)

Iteration 1:  SUB R0,R1 with R0=n=10, R1=1 → R0 = R1-R0 = 1-10 = 247  (stored as n)
Iteration 2:  SUB R0,R1 with R0=n=247, R1=1 → R0 = R1-R0 = 1-247 = 10 (stored as n)
Iteration 3:  back to 247 ...

n oscillates between 10 and 247 — never reaches 0 — infinite loop.Root cause trace

Step 5 — Two-step fix

This bug was fixed in two stages, illustrating an important point about layered systems:

Fix A (codegen workaround): With the reversed ISA, evaluate right first, save it, evaluate left into R0, move left→R1, restore right→R0. Then SUB R0,R1 gives R1−R0 = left−right = n−1. This is a workaround: correct result, but unintuitive evaluation order.

Fix B (ISA correction): The root cause was in the decode stage: it fed src0 = reg[PTR0] = Rs and src1 = reg[PTR1] = Rd, so src0 − src1 = Rs − Rd. The fix swaps the register assignments for non-immediate SUB only — src0 ← reg[PTR1] = Rd, src1 ← reg[PTR0] = Rs — in both idecode.v (RTL) and NoobsCpu.c (cmodel). The execute stage (src0 − src1) and the SUBI immediate path are untouched, so SUBI continues to compute Rs − imm correctly. Now SUB Rd,Rs = Rd − Rs, matching every other ISA. The codegen was also simplified back to the natural left-first evaluation order:

; n = n - 1  (FULLY FIXED — natural evaluation order)
    LOAD  R0,__fib_n    ; R0 = n  (evaluate LEFT)
    STORE R0,__tmp0     ; save left
    XOR   R0,R0
    ADDI  R0,R0,1       ; R0 = 1  (evaluate RIGHT)
    ADDI  R1,R0,0       ; R1 = 1  (right → R1)
    LOAD  R0,__tmp0     ; R0 = n  (restore left)
    SUB   R0,R1          ; R0 = R0-R1 = n-1 ✓ (Rd = Rd-Rs, conventional)
    STORE R0,__fib_n    ; stores n-1 ✓Final fixed assembly
Lesson: Fix at the Right Layer

A workaround in a higher layer (codegen) can paper over a bug in a lower layer (ISA/RTL), but it adds hidden complexity and surprises anyone writing assembly by hand. The correct approach — once the root cause is understood — is to fix the lowest layer so all higher layers can use the natural, expected interface. Always run test programs through the cmodel (simulator) to catch semantic errors, not just the assembler.

Bug 2: The Assembler Section Detection Bug

Symptom

Assembling bubble_sort_compiler_gen.asm produces hundreds of "Argument X isn't numeric" errors. Tokens appear as XORR0, LOADR0, JMPNC__label — concatenated strings.

Diagnosis

The concatenated tokens XORR0 (opcode + register with no space) indicate the assembler is not seeing line separators properly. But the file looks fine. The real clue is which instruction the errors start after: they start right after a STORE R0,data instruction.

The assembler uses this to detect sections:

if($line =~ /data/) {   # matches ANY line containing "data"
    $data_section = 1;
    $code_section = 0;
}noobsASM.pl (buggy)

The bubble sort example has a global array called data. The generated instruction STORE R0,data contains the substring "data" — so the assembler silently re-enters data-section mode mid-program! All subsequent code instructions are then parsed as raw data bytes, explaining the mangled tokens.

Fix

if($line =~ /^\.data$/) {   # matches ONLY the exact section header ".data"
    $data_section = 1;
    $code_section = 0;
}noobsASM.pl (fixed)

Anchoring with ^ (start of line) and $ (end of line) and requiring the leading dot means only the literal string .data on its own line triggers a section switch.

Lesson: Avoid Substring Matching for Structured Data

Matching /data/ when you mean "the section header .data" is a classic case of over-broad pattern matching. Any time you're looking for a specific structural marker, use the most precise match possible. A variable named database, mydata, or simply data would all trigger the same silent failure.

Key Takeaways

  • Each phase has a clear contract. The lexer produces tokens; the parser consumes tokens and produces an AST; semantic analysis enriches it; codegen emits text; the assembler emits bytes. Clear interfaces make each stage independently testable.
  • The ISA drives all codegen decisions. Before writing a single line of codegen, read the instruction set exhaustively. Subtle ISA quirks (like reversed SUB operands) become catastrophic bugs if discovered late.
  • Invariants simplify everything. The invariant "R0 always holds the expression result" means every codegen helper can be written in isolation without worrying about what registers are live.
  • Static analysis (parsing + semantic) is cheap; runtime bugs are expensive. The more you catch at compile time, the fewer surprises at runtime.
  • Test with a simulator. A syntactically correct assembly file tells you nothing about correctness. Run every generated program through the cmodel (CPU simulator) and check the output memory to verify behaviour.
  • Be precise with pattern matching. /data/ and /^\.data$/ look similar but behave very differently. Always use the most specific match.
